## Provenance

- Recorded 22 September 2026 (UTC) in the development environment used
  to build this project (Ubuntu 24.04 container), not on Hiten's machine.
- Command: `tcpdump -i lo -nn -s 0 -w evidence/pcaps/20260922T115026Z-containment.pcap 'tcp and port 6380'`
- During the capture, restriction action 3 (CASE-00006, source
  127.208.20.16, Redis only, 15 minutes) was approved through the API,
  then one connection was made from the restricted address and one from
  an unrestricted address. 23 packets.

## What the packets show

| Packets | What happened |
|---|---|
| #1 to #6 | Verification probe from 127.208.20.16. The TCP handshake completes (#1 to #3), then the lab sends FIN 0.08 ms later (#4) without any Redis data. The guard counted this refusal, so the action was marked verified. |
| #7 to #13 | Manual test from 127.208.20.16. Handshake (#7 to #9), FIN from the lab (#10). The client still sends `PING` (#12) and the closed socket answers with RST (#13). The client read nothing. |
| #14 to #23 | Control test from 127.208.20.98, which is not restricted. The client sends `PING` (#17) and Redis answers `+PONG` (#19). The service was healthy the whole time. |

## What this does and does not prove

The block works at the application: new connections from the restricted
address are closed before any service data. It is not a firewall rule.
The kernel still completes the TCP handshake, which is why #1 to #3 and
#7 to #9 exist. A port scan from the restricted address would still see
port 6380 as open. docs/limitations.md says the same.
